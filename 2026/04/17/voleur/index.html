HTB Voleur Machine

Created2026-04-17|Updated2026-05-26
|Post Views:

Voleur is one of HTB’s most popular medium rated Active Directory machines. It begins with an assumed breach scenario, providing credentials for a mock user. Upon enumerating the Windows services, the attacker will find NTLM authentication to be disabled, disrupting the typical workflow. After overcoming this obstacle, an encrypted document is found containing several credentials. These credentials can be leveraged to perform a targeted kerberoast on two users. However, these two users do not lead to further privilege escalation. Instead, it can be found in the group privileges of one of the service accounts, the ability to restore a deleted user. This deleted user has access to more encrypted credentials, which in turn have access to an anonymous SSH private key. Within the SSH instance, the attacker will find a mounted backup for ntds.dit, exposing the administrator hash.

Initial Enumeration

Nmap reveals a whole set of Active Directory ports, weirdly including ssh on 2222 as well.

Since we begin with credentials, we’ll perform some basic authenticated enumeration against SMB and LDAP. However, we’ll quickly see that some security measures have been put in place.

Exploiting SVC_LDAP

The todd.wolfe user seems important and I have a suspicion it’ll play in later. However, for now, we’ll see what can be done with the exposed service accounts in bloodhound.

Svc_iis doesn’t show anything interesting, but svc_ldap can targetedKerberoast svc_winrm.

I’ll get a TGT for svc_ldap, so I can use targetedKerberoast without any errors.

We get two kerberoast hashes, but only one is crackable.

Lacey.miller avails nothing; svc_winrm does.

Since svc_winrm is part of the remote management group, we can login and find the user flag.

Restoring Todd.Wolfe

There doesn’t seem to be much in any of the directories, except I notice that todd.wolfe has his own home directory.

When I look to see local account users, he’s still missing as expected.

After doing a bit of research, it looks like the recycle bin needs to be enabled for the restoration process to occur. From what I can tell, it hasn’t been disabled, so we should be able to restore what’s in the deleted container. First, we’ll need to get into a svc_ldap shell, since it’s the one with the restore user group privileges. We can use RunAs to do this. Start a listener and run the executable.

Now, we can enumerate the deleted object and restore the account.

Inside his home directory, we find nothing particularly special or interesting. Although at C:, an IT folder is accessible, also being exposed over smb.

The IT folder for this user contains an “Archived User”, todd.wolfe. It seems to be an old copy of his home directory.

Within user home folders, we know to check the AppData directory since credentials are sometimes stored there. In this case, we do find encrypted data and the masterkey in an adjacent directory.

After obtaining both with the “get” command, we can decrypt the masterkey and then the credentials using DPAPI.py, the impacket tool for attacking Windows’ built-in cryptographic service.

Leveraging Backups to Obtain Admin

Noticing a pattern with the group structure, I enumerate the very same share to find SSH keys along with a note.

The note reads:

Jeremy,

I’ve had enough of Windows Backup! I’ve part configured WSL to see if we can utilize any of the backup tools from Linux.

Please see what you can set up.

Thanks,

Admin

I remembered hearing about Jeremy sometime before, and I realized it was from the Excel document.

It’s mentioned alongside the svc_backup user, which would be the most likely candidate for well… any backup activity. I try the SSH keys with the svc_backup username and it works!

As habit of enumerating linux machines, I check sudo privileges.

Looks like we’re root, but that doesn’t really mean anything. Since it’s not about escalating, I poke around some more and find the c drive mounted.

There’s nothing special about HR or Finance, leading me right back to the IT folder. I expected to be missing something; instead, I found another directory within Third-Line Support.

Inside, it looks like there’s a backup to the whole ntds.dit file, which would mean domain compromise if it’s still valid.

I try the normal way of spinning up a python http server to download the file. However, I never receive a callback, so I instead use upload server.

Getting ahead of myself, I attempted to dump the credentials.

Looks like I needed the SYSTEM hive file, which is thankfully within the registry folder right next to it.

Using the same file upload method, I obtained the two files and ascended to Windows Admin.

Beyond the Flag (Vulnerability Analysis)

Just Bad Management

Voleur is one of those machines that highlights the exploitability of simple misconfigurations and ignorance. Not once are we required to unleash a zero-day or devastating CVE (i.e. printnightmare). Instead, all that’s required is cracking weak passwords and passing them around the environment. If there’s anything that could be classified as a “vulnerability”, the truth is that it’s baked into Windows, made dangerous by each individual user. Although there aren’t any “patches” that need to be made to Voleur, it could certainly use a better password policy, stricter storage procedures, and detection measures for things like Kerberoasting. Also, maybe don’t trust Jeremy with secure backups.
